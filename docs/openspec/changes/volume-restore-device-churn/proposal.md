# 提案：录音 ducking 恢复在设备重枚举/瞬时失败时被永久放弃

## 问题描述

用户报告：录音结束进入「识别处理 → 识别完成」途中，系统输出音量「消失」——实际是音量停留在录音时的压低值（用户设置降低 70%，基线 63% 时卡在约 19%），需要手动调回。与项目记忆中「提示音全没了/没效果」故障同根：提示音其实正常播放，只是系统音量停在压低值。

## 根因分析

音量 ducking 引擎（`crates/platform/src/volume.rs`）在真实硬件上单独驱动（duck → hold → restore，含还原中途再次录音）表现正确；丢音量发生在恢复阶段遭遇设备环境变化时，两条缺陷叠加：

1. **恢复不对称的放弃语义**（`volume.rs` `tick_restore`）：恢复期间一次 `snapshot()` 失败即 `lease = None` 永久放弃（注释「安全放弃恢复」）；而录音阶段（`tick_active`）同样的失败只是跳过本 tick 重试。设备重枚举引发的瞬时读取失败落在恢复窗口（约 450ms）内，音量就永远停在压低值。
2. **用易变的 AudioObjectID 寻址设备**（`mac.rs` `output_volume_for`）：租约记录的 `native_id`（AudioObjectID）在 macOS 设备列表变化（动态设备上下线、开关麦克风触发的枚举、显示器睡眠唤醒）时会被重新分配；恢复时直接以旧 ID 寻址，失败即触发上一条的放弃。稳定标识是 UID（`device_id`），但恢复不按 UID 重新解析。

触发源与「识别处理/完成」窗口重合：`stop_recording` 发出恢复意图后立即关麦（`r.stop()`），识别完成回到 Idle 时 `refresh_meter` 重新开麦，加上系统动态设备（如「Xs Microphone」连续互通麦克风）自主上下线，都可能在约 450ms 恢复窗口内造成设备重枚举。

## 修复目标

1. 恢复阶段具备韧性：设备对象 ID 失效时按 UID 重新解析同一设备并继续还原；瞬时读取失败重试而非放弃；只有设备 UID 确认消失才放弃恢复（保留现有安全语义）。
2. 所有权规则不变：重解析后发现实际音量已被用户改动，仍立即让权，绝不覆盖用户选择。
3. 编排层不主动在恢复窗口内制造设备枚举活动（电平表重启移出恢复窗口）。
4. 回归测试覆盖「恢复中设备对象 ID 变化仍能完成还原」。

## 影响范围

- `crates/platform/src/mac.rs`（按 UID 重解析设备）
- `crates/platform/src/volume.rs`（恢复韧性 + 单测）
- `app/src-tauri/src/controller.rs`（电平表重启时序）

无新增能力、无公共 API/数据格式变更、无跨模块架构调整。
